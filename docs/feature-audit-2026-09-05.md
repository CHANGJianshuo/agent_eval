**P0：先解决会误导结论的问题**

1. **零权重可能把失败评成满分。**

   离线构造一个 completion 评分项，weight=0，Judge 给 0 分。实际结果为 `task_score=1.0`、`passed=true`、`status=complete`。原因是维度没有正权重时默认满分，整体又允许该配置运行。这是边界配置缺陷，不表示现有全部任务已经产生此问题。

   建议：启动时拒绝没有有效评分依据的配置；评分层再次兜底，缺少必要评分依据时不给通过结论。零权重作为禁用项是否允许，可以保留明确规则，但禁用所有评分项不能变成通过。不要把问题交给操作者自行记住。

   依据：[scoring.py](../src/claw_eval/graders/scoring.py)、[rubric.py](../src/claw_eval/graders/rubric.py)、[启动预检](../src/claw_eval/api/routes_tests.py)。现有 validator 的零权重检查只是 warning，接入它后仍需加强这条规则。

2. **对话失败的用例会从报告完成率中消失。**

   离线提交 2 个用例，一个正常、一个模拟网络超时。CLI 正确返回失败，`outcome.json` 正确记录 expected=2、evaluated=1；HTML 却显示“完整评分 1/1”。报告只扫描已有结果文件，缺少失败用例的位置。

   建议：用运行的完整用例清单作为明细和分母来源，合并结果与失败状态。展示计划数、对话完成数、评分完成数、异常数；每个未完成用例都能找到原因。通过率仍以完整评分为分母，但完成率应为 1/2。损坏文件需要显式报错，不能静默消失。

   依据：[batch outcome](../src/claw_eval/cli.py)、[报告构建](../src/claw_eval/report/builder.py)、[聚合](../src/claw_eval/report/aggregate.py)、[报告模板](../src/claw_eval/report/templates/task_page.html.j2)。

3. **安全红队异常样本会降低破防率。**

   离线输入一个明确破防用例和一个 Judge 异常用例，整体破防率为 50%；只有异常用例时为 0%。有效安全判断中实际是 1 个用例、1 次破防。与此同时，`safety-test` 捕获执行异常后仍继续正常结束，且产物默认使用任务级文件名。

   建议：沿用普通 batch 的用例清单、快照、失败状态和运行目录，删除独立执行循环；独立展示安全评分覆盖率和已确认破防数。未完成安全判断的用例不能视为安全；零有效样本显示“无法判断”。

   依据：[红队统计](../src/claw_eval/adversarial.py)、[safety-test](../src/claw_eval/cli.py)。

4. **人设标签与实际模型输入脱节。**

   固定态度、剧本、历史与 seed，仅改变年龄、学历、性别和 MBTI。两个 persona 的标签不同，捕获到的模型消息却完全相同。当前这些维度用于采样和分组，没有成为模拟行为的控制条件，因此不能把分组差异解读为年龄等因素造成的效果。

   建议：先隐藏未生效的行为配置与相应效果归因；保留已有效的态度、剧本和噪音控制。需要新增模拟能力时，优先用可描述、可检查的行为条件，例如信息掌握程度、配合意愿、表达方式。不要仅为了保留“五维度”展示而增加未经验证的人群假设。

   依据：[build_persona](../src/claw_eval/persona_factory.py)、[UserSimulator](../src/claw_eval/user_simulator/simulator.py)。另已复现：自定义维度能在配置 API 保存，但运行校验会拒绝，应先限制为引擎实际支持的维度。

5. **历史数据迁移与详情使用不同评分口径。**

   将一个旧版“跳过 Judge 但 passed=true”的结果迁入临时数据库，数据库通过率仍为 100%；同一结果经当前模型读取后 `passed=null`。卡片指标和具体结果可能互相矛盾。

   建议：迁移与重算统一使用当前结果模型和聚合规则；对已经导入的历史记录提供可审查的指标重算，不修改原始 trace。旧记录缺少快照的事实要继续保留。

   依据：[migrate_existing_traces](../src/claw_eval/db/repo.py)、[结果完整性规则](../src/claw_eval/models/trace.py)。

**现有任务的覆盖提醒**

`rider_delivery_demo_0904` 的 `faq.multi_day_contract`、`behavior.out_of_scope`、`behavior.hang_up_after_comfort` 被静态检查标为缺少触发覆盖。它们使用 user_keyword，当前 validator 只在显式探针中查找关键词。这说明没有确定性的探针覆盖证据，不能据此断言 LLM 自然对话中永远不会触发。建议把提示改为“未设计确定性覆盖”，并补针对性用例、统计实际触发率。

依据：[check_trigger_reachable](../src/claw_eval/validator.py)。

**P2：按使用规模补齐，不先扩大架构**

继续单人本地使用时，优先完成上述结论和流程问题。准备供团队持续使用时，再把以下能力作为上线验收项：

- 登录与项目权限，报告和原始对话的访问限制，修改和删除操作留痕。
- 单机全局限流、调用次数与 token 用量、耗时和失败类型记录，任务预算控制。
- 数据库、配置、运行快照与结果的一致备份，以及实际执行过的恢复演练。
- 依赖版本固定、部署与版本回退说明；在目标机器上验证负载和长任务恢复。
- 将“审核 → 启动 → 部分失败 → 报告 → 建议 → 候选版本 → 回归”纳入浏览器验收。用替代模型跑确定性的失败场景，另设小规模真实模型校准。

当前只有文本模型 SUT 适配。若目标是评测已部署的业务 Agent，再增加明确的 HTTP/会话/工具调用契约；若目标包含电话音质、识别错误或语音延迟，再单独定义音频评测范围。不要把文本噪音模拟扩称为完整电话链路验收。

**应该保留、删除和简化什么**

- 保留共享评分器、冻结运行输入、固定用例清单、结果原子写入、运行隔离和持久任务状态。这些都直接服务于评测可信度，无需换框架重做。
- 先隐藏未生效的人设行为维度、不可运行的自定义维度，以及“保证覆盖”“可信”这类证据不足的表述。
- 回归是用户明确需要的功能，应真正接通；接通前去掉可操作但没有结果的占位交互。噪音编辑同理，先提供简单表单，不必先做复杂编辑器。
- 将安全测试和旧 pipeline 的执行逻辑收敛到普通评测流程，减少不同入口的评分、快照和失败口径差异。
- 确定 React 为主入口后，先迁移旧 Streamlit 中仍有价值的建议应用、版本、变量和噪音编辑，再删除重复 UI。现在直接删除会丢失已有功能。
- 先让人工采纳建议、修改和验证可用，再考虑自动应用建议。暂时不增加多 Agent 编排、分布式队列或大规模调度体系。

建议交付顺序：先完成 P0 的五类一致性修复；随后交付建议与固定基准回归流程、配置与校准完善；最后按实际团队使用需求补运维能力。每一阶段以表中的可观察验收标准为完成依据。
